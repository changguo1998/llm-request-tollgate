# 速度指标调研与结论

> 主题: 如何从每笔请求的日志字段计算"模型速度", 使同一性能下短请求与长请求得到接近的
> 数值, 即速度代表"性能"而非请求长短.
> 数据: `var/requests*.jsonl`, 2026-11-03 至 11-12, 约 2.9 万笔成功流式请求 (筛掉缺
> 字段与失败样本). 结论为一次调研的快照, 参数随参考窗重算.

## 1. 原生日志字段与速度的派生关系

请求日志 (`src/log.go` 的 `logRec`) 按请求记录但不直接记"速度", 速度是派生量:

| 字段 | 变量 | 含义 |
|---|---|---|
| `usage.completion` | c | 输出 token 数 (上游缺 usage 时为字符估算, 此时 `missing_usage=true`) |
| `decode_ms` | d | 解码段时长: 首字节到流末, 仅流式有值 |
| `ttfb_ms` | t | 首字节时延: 从代理真正向上游发包到收到首字节 |
| `usage.prompt` | p | 输入 token 数 |
| `bytes` / `bps` | b / bps | 响应体字节数与字节速率 (流式) |
| `tps` | - | 每请求解码速率 c/d, 已派生但 TUI 聚合不用它, 一律重算 |

`tps` 的存在条件: 流式且 d>0 且 c>0. 度量上 t 与 d 不重叠 (t 在首字节前, d 在首字节后).

## 2. 代码库现有平均口径盘点

| 名称 | 位置 | 算法 | 用途 |
|---|---|---|---|
| `tokRate` 平均 | `src/rate.go:28` | Σc / Σd (体积加权, 空闲不计) | 低吞吐绝对门槛 |
| `tokRate` 峰值 | 同处 | 单笔最高 c/d | 低吞吐峰值门槛 |
| `avgRate` | `src/rate.go:47` | 各笔 c/d 的算术平均 | 相对门槛的分子 |
| 历史平均 | `src/gate_state.go:25` | perfSum/perfN (各笔速率算术平均, 终身, 落盘) | 相对门槛的分母 |
| `rateShow` | `src/rate.go:66` | 窗口内各笔 c/d 的算术平均 | TUI 三列速度 |
| `ttfbAvg` | `src/tui_tok.go:45` | 各笔 t 的算术平均 | TUI 首字节行内/顶栏 |
| `avgLat` | `src/gate_lowperf.go:130` | 各笔 t 的算术平均 | 高延迟门槛 |

非平均项: 峰值/谷值取极值, 顶栏流量是 Δbytes/Δt 的瞬时值, 配色权重是高斯衰减求和,
缓存占比是比例. `-summary` / `-usage` 与 `analysis/` 只求和. 全项目没有中位数或分位数.

关键不一致: TUI 显示用 1h 等权算术平均, 调度器判定用 10min 体积加权, 二者同名"平均"
但数值可差 1.5 至 2 倍; 历史基线终身累积且不显示. 排查"为什么没锁/为什么锁了"需同时
读 TUI 表, 事件页与 `var/gate-state.json`.

## 3. 相关性结论 (实测)

### 3.1 t, c, p, d, r = c/d 的相关

- c 与 d: 强相关 (模型内对数相关约 0.84), 结构性, 不是两个独立变量.
- t 与其它全部弱: 原始相关均在 0.1 上下; 与 p 的相关 (模型内约 0.32) 来自长输入的
  预填充, 弹性次线性 (log-log 约 0.2-0.33).
- r 与 d: 强负相关 (全体对数 -0.64), 但这是代数投影: 实测 corr(log d, log r) = -0.638,
  而由 r=c/d 与实测方差推出的投影值 = -0.653, 两者几乎相等. 模拟验证: 速率真常数时
  d-r ≈ 0; 只有输出增长慢于解码时间 (弹性 < 1) 时 d-r 才为负. 本数据弹性约 0.5.
- r 与 c: 每模型符号不同且随负荷漂移 (见 §4), 不是稳定关系.

### 3.2 日周期 (1h 分段)

- 日内周期存在且是上游级的: 各模型日内 med r 的 max/min 从 1.5x (arkcp) 到 6.2x
  (deepseek-flash); deepseek-flash 傍晚 ttfb 中位曾到 43s.
- 部分模型只在窄时段活跃 (v4.1flash-off 仅 16-23 时, gemini 仅 9-17 时), 其"全天平均"
  只代表该窗口.
- 理想小时 (该模型 med r 属其全部小时前 40% 且 med t 属后 40%) 的规律:
  - c-d 对负荷免疫 (理想小时仍 0.67-0.99).
  - c-r 在理想小时把"负荷假象"与"内在属性"分开: gpt6/kimi 归零 (负荷造成),
    arkcp 仍负, codex 仍正 (内在).
  - p-t 与 p-d 在理想小时反而更强 (全体理想小时约 0.47/0.49): 负荷噪声掩盖了
    "长输入 → 预填充更久"这条计算路径.

## 4. 平均口径的权衡与否决项

六种口径在"长度构成变化"下的稳定性 (短 30% vs 长 30% 子集相对差):

| 口径 | 全体 | gpt6 | dsf | kimi |
|---|---|---|---|---|
| 等权算术平均 | 186% | 6.9% | 59% | 26% |
| 体积加权 Σc/Σd | 51% | 69% | 14% | 7.6% |
| 几何平均 | 40% | 52% | 3.4% | 16% |
| 中位数 | 24% | 59% | 13% | 19% |
| 截尾平均 (10-90%) | 22% | 42% | 1.6% | 16% |
| 长度分层带宽均值 | 13% | 55% | 8.1% | 15% |

结论: 没有通吃的口径; 等权算术平均在全体上被微输出右尾带崩 (186%). 调度器的体积加权
保留 (它是容量口径, 管锁判定); 显示侧用等权是历史遗留, 与判定不同率.

否决项: 按长度分带 (分段) 的方案被明确否决, 不光滑, 投机取巧, 一律不采用.

## 5. 参数公式的推导历程

尝试过并被数据否定的候选:

- 幂律 `r = c/(A·d^β)`: 参考窗内压不平 gpt6/dsf (0.52/1.57 等), 因为曲线形状非幂律.
- 高阶多项式 + 稳健拟合 (K=2/4/6, IRLS): 无实质改善, 说明失败不在公式阶数.
- 引入 prompt 长度 L: prompt 指数逐模型符号分裂 (gpt6 -0.39, dsf +0.16), R2 仅 1-8%, 不稳定.
- 注意力增长项 `γ·(L+i)`: d/c 对 c 与对 L 的回归斜率几乎没有稳定正值, R2 < 2%.

物理机制 (联网资料): 解码是内存带宽约束, 每 token 读一遍完整权重, 单流速率上限 =
带宽/模型字节, 与长度无关; 真实速率 = 上限 × 投机接受率 × 批共享. 投机接受率取决于
输出内容的可预测性 (实测同一台机器可预测内容 103 t/s vs 开放散文 19 t/s), 批共享由
并发决定. 两者都不在 (c, d, p) 里, 这是单请求速率的不可约噪声来源.

关键遗漏的观测变量: 日志里的 `bytes`. `bytes/completion` 与解码速率的相关达 ±0.1 至
±0.67, 远超 c 与 L. 它混合了两种机制: 负相关 (多模态/base64 段只记 1 token 却占大量
字节, 稀释速率, gpt6/dsf) 与正相关 (代码等可预测内容的投机接受率高, arkcp/v4.1off).

## 6. 最终公式 (定稿)

```
r* = (c / d) · (c / b)^g
```

- `c` = usage.completion (输出 token)
- `d` = decode_ms (解码耗时, ms)
- `b` = bytes (响应字节)
- `g` 每模型一个, 由该模型同态参考窗回归 `log(c/d) = a + g·log(c/b)` 拟合; `a` 是 log 空间截距 (典型速率基准), 仅作参考不参与在线计算

性质: 同一公式, 参数按模型; 无分段; 参考窗内"同一性能下短/长请求 r* 一致"成立到
±10-20% (gpt6 短档与 dsf 长尾是已知残余). r* 别名"性能 (perf)"; 典型状态附近数值
即该模型典型解码速率 (约 e^a 量级), 参数表里没有的模型退回原始速率 c/d.

当前 `g` 值 (2026-11 参考窗, 统一 frac=0.60):

| 模型 | 参考小时 (理想) | g | r* 短/中/长 |
|---|---|---|---|
| deepseek-flash | 3,5,6,7,8,9,20 | +0.79 | 0.89 / 0.97 / 1.12 |
| gpt-6-sol | 6,8 | +0.23 | 0.52 / 0.84 / 1.44 |
| kimi-k3.1-pro | 5,6,7,8,12 | +0.22 | 1.12 / 0.94 / 0.90 |
| v4-flash (ustc) | 22 | +0.34 | 1.57 / 1.07 / 0.71 |
| arkcp-economy | 0,12,23 | -0.36 | 1.19 / 0.93 / 0.81 |
| v4.1flash-off | 18,21 | -1.26 | 0.57 / 0.96 / 1.37 |

### 参考窗选择规则 (定稿)

- 样本前置: 成功流式 (status<400), t/d/c/b 均大于 0, 剔除微样本 c>=15 且 d>=100ms.
- 理想小时: 每模型按小时 med r >= p65 且 med t <= p35 的小时集合; 活跃小时不足 4 个时退化为全天.
- 典型区: 对理想小时样本的 (ln(b/c), ln(c/d)) 做二维密度 (100x100 网格, 3x3 平滑), 保留密度前 60% (frac=0.60), 近 X 轴慢尾与近 Y 轴虚高速簇自动被排除.
- 拟合: 典型区样本上 OLS 回归 `log(c/d) = a + g·log(c/b)`, g 即公式指数.
- 验证: 拟合 g 后在全体理想小时样本上按 c 三分位检查 r* 中位 (上表右列), 应接近 1.0; 小样本模型 (gpt6, v4-flash) 平整度较差, 谨慎使用.
- 参数文件 (`analysis/figs/speedref_params.json`): 每 上游/模型 存 (g, a, ref_hours, n_ideal, n_typical, frac, flatness), 顶层 `_meta` 带版本 (参考窗) 与生成时间戳.

## 7. 落地前提与边界

- 参数由代理周期性重算: 用全部日志 (var/requests*.jsonl) 在 Go 内重算 (src/perfref_recompute.go), 驻内存; 每次周期随日志增长漂移; g 对选样/网格细节敏感, 与参考脚本存在浮点级差异, 跨版本不可直接比.
- 参考窗必须同态: 对 deepseek-flash 这类多状态模型, 要先砍掉拥塞时段再定窗.
- 在线只用日志行的 c/d/b 重算 r*, 与仓库"不信任派生字段"的做法一致, 不改日志 schema.
- 不替换调度器的体积加权 (那是容量口径); r* 是长度归一的性能口径, 供比较与告警.
- 剩余噪声边界: 投机接受率与批共享不可观测, 单请求 r* 抖动不可约; 如需继续降噪,
  需补日志字段 (如 reasoning 占比, 分段字节计数), 目前没有.
