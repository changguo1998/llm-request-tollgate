# llm-request-tollgate — 顶层设计

> 状态：第一版已实现 (main.go 单文件代理 + test/ 假上游自测, 82/82 断言全绿,
> 2026-10-13; 预算闸门 D12、日志按天轮转、用量分解命令 `-usage` 同批加入)。
> 实现形态是自研单文件代理，不加插件，不引入现成网关。
> O1/O2/O3/O5 已实现（常驻自检 / -summary 汇总 / source 标识 / GET /v1/models）。
> 文末附录保留已否决路径的调研记录，备查不再执行。

## 1. 需求

### 1.1 模型路由

- 一个对外模型名绑定一组后端候选，形如：
  `deepseek-v4.1-flash: [ustc/deepseek-v4.1-flash, group/deepseek-v4.1-flash, arkcp/deepseek-v4-1-flash, arkap/deepseek-v4-1-flash-260910]`，配置里的等价写法见 §4.8。
- 同一列表内候选一律视为完全相同；顺序即优先级，由用户自定义。
- 别名表即白名单：未在表里的模型名一律拒绝（404 带 OpenAI 兼容 error 体），不猜上游。
  代理对外 `GET /v1/models` 返回别名（逻辑名）清单，不暴露上游真实 id（O5）。
- 对外隐藏 provider：请求侧只暴露代理地址与逻辑名；响应体与流 chunk 里回显的 `model`
  字段已改回请求的逻辑名（O9 已实现）。

### 1.2 失败切换

- provider 报错时，代理就地换后端重发，对 agent 透明——agent 只看到等待变长。
- agent 侧不改：不调整各 agent 自己的重试策略与配置。
- 代理不再重试时，把真实错误原样交给 agent，保留原始状态码与关键响应头。
- 现状：代理层已做**集中 fallback**——候选按序尝试，只在首字节前（传输失败 /
  上游 429 / 5xx）切换下一个；全部失败保留最近一次错误原样透传。其余 4xx 不重试，
  避免「模型名写错」这类请求空转（§4.5）。首字节之后不能切后端，物理限制见 §2 第 1 条。

### 1.3 请求侧限速

- 排队、严格最小请求间隔与并发上限。最小间隔由令牌桶的补充速率承担，突发容量吸收峰值
  （「每分钟 N 次」这类额度就表达成速率 N/60 加一个突发容量），并发由信号量承担
  （§4.3 与 §5.1 D3）。
- 按「上游 + 凭据」分组，跨 agent 共享同一份计数；各上游互不拖累。
- 覆盖机器上所有 agent：本机所有会发模型请求的进程都必须走代理。
- 目的是防止频繁访问上游，不是节省 token 花费。

### 1.4 金额预算控制

- 目标不变：超限拒服务。
- 口径改为查上游余额接口，不再本地按窗口累计花费。原来的日 / 月窗口口径降级为日志与
  汇总的统计口径，不再当闸门用。
- 实测 (2026-10-13)：USTC 的余额接口 (网页面板 `/api/usage/quota` 等) 只认 cookie
  会话，不接受 `sk-` API key (401 "Invalid session")，代理持 key 调不到。因此闸门落地为
  D12：代理定时从请求日志重建「滚动窗口 token 累计」，任一窗口满额即拒服务——上游
  限额 (该 key 自带 3h/12h/24h 三层预算，平台侧硬拒) 仍是最硬的一层，代理闸门负责
  提前拦截。

### 1.5 可观测

- 看得到实际使用了哪个后端、用了多少量。
- 花费不在代理内估算（不建 token 单价表），改由上游余额接口提供；第一版未接。
- 代理内部日志加本地查询面；提示信息可接受，不为「完全无痕」牺牲功能。

### 1.6 形态

- 独立代理程序（进程外），不做 agent 内插件。

### 1.7 已砍掉

- **响应侧逐块 TPS 节流**（拖慢上游吐字）与实时 TPS 展示。它是唯一必须在「写给
  客户端之前」干预的功能；砍掉之后不再需要插件层，也就不需要动态链接构建、
  Go 版本与依赖版本对齐、以及随之而来的重编负担。

## 2. 已探明的硬约束

1. 透明重试只在「给下游写出第一个字节之前」成立。开始写之后只能把错误原样传下去。
   这是物理限制：重发会让下游收到两段拼接的输出，比报错更糟。
2. 错误原样透传分两种位置：
   - 首字节之前：原封不动的 HTTP 错误响应（状态码 + 响应头 + 响应体）。
   - 流开始之后：响应头已发出、不可更改，只能用流内部约定的报错形态表达（本设计取
     SSE error 事件后关流，见 §5.2 F6），不能塞 JSON 错误体，否则下游可能把半截流
     当作正常结束。
3. 客户端对「两块之间的间隔」有 5 分钟静默线（宿主 `streamIdleTimeoutMs`，默认
   300000，可配置）。代理的出流节奏与任何等待都必须留在此线以内。
4. 代理成为本机唯一模型出口，因而是单点故障；密钥也集中到代理一处。
5. 所有流量必须真的走代理：只要有一个 agent 直连上游，限速总闸就失效。
6. 限速必须按「上游 + 凭据」分组，不能做成单一全局总闸，否则不相关的上游互相拖慢；
   同一上游同一凭据的计数需要跨 agent 共享。
7. 代理只监听本机、走 HTTP 即可，不需要自建 CA 或签发证书——各 agent 的 base URL
   直接指向 `http://127.0.0.1:8787/v1`（端口可配，见 §5.2 F8）。

## 3. 为什么不用插件

**决定性原因：限速要覆盖同一台机器上的所有 agent。** 进程内插件只能限住它所属的
那一条链，管不到同机其他 agent；而限速一旦漏掉任何一个直连上游的进程，总闸即失效。
同理，任何只覆盖单个 agent 的方案都不成立。

实际情况：同机的多个 agent 各自配置了指向同一批上游的 base URL，也就是说它们当前
就在同一份上游配额池里互相挤。只有把出口收到代理这一层，才能统一覆盖。各 agent 的
base URL 都可以改（有的在配置文件里，有的支持 profile 或临时覆盖）。

**插件的局部价值（备查，不做）**：某些 agent 宿主在请求错误处暴露了 waterfall 钩子，
注册一个监听器即可否决内建的同类重试并改判为「重试」，从而在单侧实现自动切上游 ——
不碰上游、不需要代理。但覆盖不到其他 agent，且与代理机制重叠，故不采用。

## 4. 已定案的实现（自研单文件代理）

### 4.1 形态

单进程，内含五件事：别名表、按「上游 + 凭据」分组的令牌桶与信号量、
`httputil.ReverseProxy` 透传、响应 usage 提取与用量记账、预算判定点 (D12：定时从
日志窗口累计, 满额拒服务)。

- 所有 agent 打同一个进程，计数天然跨 agent 共享，无需 Redis 或数据库。
- 严格最小间隔取令牌桶补充速率（比「时间窗内 N 次」更贴需求）；并发上限取信号量。
- 桶空时排队；超过等待上限（默认 60 秒）返 429 带 `Retry-After`，交给 agent 自身的重试。
- 分组键是「上游 + 凭据」，即一个 base URL 加一把 key 一份计数，各上游互不拖累（§2 第 6 条）。
  第一版一个上游只配一把 key（§5.3 O6）。

### 4.2 别名表

- 结构：`逻辑名 → [(上游, 该上游的真实模型 id), ...]`；候选顺序即优先级。
- 必须逐上游写真实 id，不能按名字在候选间平移：`deepseek-v4-flash` 在 ustc/group
  与 arkcp 下不是同一个版本。
- 别名表即白名单：未命中的模型名直接返 404（OpenAI 兼容 error 体），不猜上游。
- 别名表兼作路由表：查一次得到真实 id 与目标上游。

### 4.3 限速与用量

- 分组键是「上游 + 凭据」：每个 base URL 加每把 key 一份计数，各上游互不拖累（§2 第 6 条）。
- 令牌桶按分组，参数是补充速率与突发容量；严格最小间隔取补充速率，并发上限取信号量。
- 桶空时排队；等待上限默认 60 秒，超过返 429 带 `Retry-After`，交给 agent 自身的重试。
  排队等待与上游首字节之和仍远小于客户端 5 分钟静默线（§2 第 3 条）。
- 用量获取：转发时把请求体的 `stream_options.include_usage` 强写为 true，从流末
  usage chunk 取用量；非流式直接读响应体的 usage。
- 缺 usage 时按字符数估（口径见 §5.2 F7），并把「没拿到 usage 的请求数」记入日志。
- 只记 token 用量，不建单价表、不在代理内估算花费（§1.4 与 §5.1 D7）。原来的「事后
  计账、下一笔才被拦」随本地窗口预算一起推迟。
- 计数与账本都在进程内，不落盘；重启清零，明细靠日志（§5.1 D6、§5.2 F5）。

### 4.4 可观测

- 每次请求记：逻辑名、命中上游、真实模型 id、token 用量、是否缺 usage、是否被限速排队。
- 花费不在代理内记（§1.4）；余额与花费走上游余额接口，后续接入。
- 提供本地查询面：JSONL 日志 + `-summary` 汇总命令（O2 已实现）；`-summary` 传目录
  会汇总目录下全部 `*.jsonl`，跨天归档也能一起看。
- 用量记三种输入口径：`prompt` / `cached`（命中缓存的输入 token）/ `completion`，另记
  `total`。缓存价通常是输入价的 1/10，标定系数时必须分开看，所以代理把上游的三种
  缓存字段名（`prompt_tokens_details.cached_tokens`、`prompt_cache_hit_tokens`、
  `cache_read_input_tokens`）都解析进来。
- `-usage <log|dir>` 按 上游 + 真实模型 × 窗口（`-windows`，缺省 3h/12h/24h，另加「全部」）
  列出请求数 / 缺 usage 数 / 四类 token，用于标定预算折算系数：
  系数 = 平台已用额度 ÷ 该模型窗口内 `total`，按真实模型 id 填进 `budget.units`。
- 日志按本地日历天轮转：跨天（或隔天启动）时把上一段日志归档为
  `<base>-YYYY-MM-DD.jsonl`，同名不覆盖（依次 `-1`/`-2`）；归档不自动删除，留存交给外部。
  预算聚合跨归档读最近窗口内的文件，因此窗口跨越午夜也不会漏算。

### 4.5 实测依据（实测直连）

对候选上游逐个探测接口面，结论落进配置（可 grep），具体地址不入库：

- 四个上游的 `/chat/completions` 与 `/responses` 均可直连成功（其中一家首字节约
  19 到 25 秒，属常态，须放大超时而不是当作故障）。
- 有一个上游连 `/models` 都不提供，其路径形态须手工确认后再接入。
- 各家都在模型名不存在时先报错（403 或 400 或 404），所以「模型名写错」会表现为
  4xx 而不是 5xx，重试判定要据此区分。
- 真实模型 id 清单须以各上游 `/models` 为准；不同上游的清单规模差异很大。

**一条最容易踩的坑**：真实模型 id 与逻辑名不是一一对应。同一个名字在不同上游可能
指向不同版本，因此别名表必须逐上游写各自的真实 id，不能按名字在候选间平移。

### 4.6 已知缺口与风险

1. 首字节之后不能切后端的物理约束仍在：集中 fallback 只覆盖首字节之前的失败
   （传输错误 / 429 / 5xx），流开始后的失败按 F6 走 SSE error 事件。
2. 集中 fallback（D10）与熔断（D11）均已实现。
3. 第一版转发只覆盖 `/chat/completions`：`/responses` 一律 404；`GET /v1/models`
   返回别名（逻辑名）清单（O5 已实现）。
4. 代理内看不到花费，只有 token 用量；缺 usage 的上游会让用量偏低。按字符估算的兜底
   与日志计数必须做，不能静默。
5. 代理成为唯一出口，即单点故障，且密钥集中于此；常驻方式与自检脚本待定（§5.3 O1）。
6. 一个上游只配一把 key，没有轮换与冷却；那把 key 失效时该上游整体不可用（§5.3 O6）。
7. 上游余额接口未按预想接入（D5 原口径），「超限拒服务」（§1.4）改由 D12 承担：
   代理按日志窗口 token 累计判断，提前拦截；平台侧硬限额仍是真正的最后一道。
   折算系数 `unit` 需按网页「已用」对照标定，标定前闸门门槛可能偏高或偏低（偏高早拒、
   偏低靠平台兜底，均不放大超限）。

### 4.7 验证顺序

1. 起最小代理（只做别名与转发），把一个真实 agent 指过来跑一轮带工具调用、思考块与
   长流的会话（起步阶段由假上游按脚本回放，见下）——确认流式逐块透传，没有被缓冲
   或改写。
2. 加 `stream_options.include_usage` 注入，核对客户端收到的 usage 与上游一致。
3. 加令牌桶与信号量：最小间隔设 3 秒，验证两次请求的实际间隔；并发设 1，两个 agent
   同时发，验证排队与 429 行为。
4. 核对用量：确认日志里每笔的 token 用量与上游一致，且「缺 usage」的请求有计数。
   预算与花费不在这一版验证范围内（§1.4）。
5. 量一次代理自身开销（首字节延迟的增量），确认可忽略。

**起步方式（已定）**：第 1 至 4 步先用本地假上游自测——假上游按脚本回放含工具调用、
思考块与长流的 SSE，真 agent 指向代理。这样在拿到真实地址与凭据之前就能验收；接上真
上游后重跑同一套。限速参数在自测阶段用假值（即第 3 步的 3 秒与并发 1）。

### 4.8 配置形状（JSON）

因为一个上游只配一把 key，「上游 + 凭据」这个分组键等价于上游表里的一条记录，所以限速
参数直接挂在上游记录上，不再单列分组。

```json
{
  "listen": "127.0.0.1:8787",
  "log_path": "var/requests.jsonl",
  "timeouts": { "connect_ms": 10000, "response_header_ms": 120000, "stream_idle_ms": 240000, "queue_wait_ms": 60000 },
  "upstreams": [
    {
      "id": "ustc",
      "base_url": "https://example.invalid/v1",
      "auth_header": "Authorization",
      "key_env": "USTC_API_KEY",
      "headers": {},
      "include_usage": true,
      "limits": { "rate_per_sec": 0.34, "burst": 1, "concurrency": 1 }
    }
  ],
  "aliases": {
    "deepseek-v4.1-flash": [["ustc", "deepseek-v4.1-flash"], ["group", "deepseek-v4.1-flash"]]
  }
}
```

- `base_url` 自带路径前缀（含 `/v1`），以 §4.5 那家的实测形态为准。
- `auth_header` 与 `headers`：有的中转不用 `Authorization`（例如 `api-key`），有的要额外头。
- `key_env`：配置只存环境变量名，真 key 启动/热加载时从环境取，不落盘；缺省回落 `key`。
- `breaker_fail` / `breaker_cooldown_ms`：熔断参数（连续失败阈值 / 冷却毫秒），选配，
  缺省 5 次 / 30 秒。
- `budget`：预算闸门（选配，缺省不启用）。`windows` 是滚动窗口限额表，例如
  `{"3h": 30, "12h": 70, "24h": 100}`（键为 3h/12h/90m/7d 这类时长，值是对应的平台
  额度上限）；代理定时（`refresh_sec`，缺省 60s）从 `log_path` 重建各窗口 token 累计，
  任一窗口已用 × 系数 ≥ 上限即返 429 `budget_exceeded`。系数按模型给：`units` 是
  `{真实模型 id: 系数}`，缺省回落 `unit`，再回落 1；系数用 `-usage` 与平台面板对照标定
  （平台各模型扣额倍率不同，公开的每模型价格见 `GET /api/models/public`）。
- `include_usage`：per-upstream 开关，用来承接 O8 的探测结果。
- `timeouts.queue_wait_ms` 对应 F3 的排队等待上限。
- `aliases` 的值是 `[[上游 id, 真实模型 id], ...]`，顺序即优先级。

### 4.9 实现陷阱（写码时逐条处理）

1. gzip：非流式要读 usage 就得能解压，出站要删掉下游传来的 `Accept-Encoding`，让
   Transport 自己协商并透明解压。
2. SSE 按行解析而不是按 chunk 切：`data:` 可能多行，流以 `[DONE]` 结束。
3. 客户端断开：释放并发信号量，且不重复记账。
4. 请求体需整体缓冲才能改写 `model` 与 `stream_options`（带 base64 图片时可能几十 MB）。
5. 非流式响应也要缓冲才能读 usage。

### 5.4 前置清单

写码阶段不需要任何外部输入：转发、SSE 透传、白名单 404、限速排队、用量记账与日志都能对
本地假上游自测（§4.7）。

接真上游之前需要：

1. 四家的 base URL 与凭据（不入库）。
2. 四家是否接受 `stream_options.include_usage`（O8）。
3. 那家不提供 `/models` 的上游，其路径形态（§4.5）。
4. 各上游真实模型 id 清单，作为别名表的输入（§4.5）。
5. 各上游的速率、突发与并发参数。

切流上线之前需要：

1. 常驻方式与自检脚本（O1 已具备：`deploy/` + `test/healthcheck.sh`）。
2. 各 agent 的 base URL 配置位置与各自的请求超时，用来校准排队上限（F3）。
3. 切流顺序与回滚方案，以及「没有进程绕开代理」的验证办法（O4）。

## 6. 宿主侧背景（引用本机时需重核）

- 宿主有唯一一处决定用哪个 provider 的内部接口，每次尝试前都会跑一次，重试也会重跑它。
- 另有决定「要不要再来一次」的内部接口，宿主的重试插件挂在那里。
- 传输层改写 provider 对主链路无效，因为上游此时已解析成具体适配器。
- 宿主插件链是 waterfall 语义：监听器最外层先跑，不调 `next()` 即否决整条链。
- 宿主的重试插件只决定「重试同一步骤」，本身不切换上游；策略按 provider 配置，
  退避带抖动，并支持上游的 `Retry-After`。
- 默认可重试错误码只有 `EMPTY_RESPONSE`、`RATE_LIMIT`、`SERVER`、`TIMEOUT`、
  `TRANSPORT`；`QUOTA` 与 `AUTH` 不在其中，宿主侧不会重试。
- 上游 usage 在流末 chunk 中给出，宿主据此记账 —— 这一点对代理的用量提取有利。

## 附录 A. 已否决路径：现成网关调研（保留备查）

> 当时的结论是「不自研，采用现成开源网关」，主选 Bifrost（Go）、备选 LiteLLM（Python）。
> 该结论已于 2026-10-12 由 §4 推翻：当时的判断依据——「网关最常见的故障不是路由，
> 而是工具调用 / 思考块 / 流式翻译被破坏，所以实测不能只发 hello world，要把真实
> 会话过一遍」——仍然有效，但当时需求里含逐块 TPS 节流，而它只有插件能补；节流被
> 砍掉后该前提不再成立。A.1 至 A.3 的事实（能力覆盖、缺口、安全记录、开销对比）
> 仍可作为日后换网关时的参考。

### A.1 Bifrost 对原需求的覆盖

| 需求 | 现成能力 | 出处 |
|---|---|---|
| 逻辑模型名绑定多后端、隐藏真实 ID | Model aliasing：任意名字映射到真实标识符，响应中有记录可追溯；model catalog 加 allowed-models 控制对外暴露面 | [Aliasing Models](https://docs.getbifrost.ai/providers/aliasing-models) |

| 失败后切后端、对 agent 透明 | 原生 fallback；provider 内重试与跨 provider 切换是两个独立机制 | 同上 |
| 全部失败返回真实错误 | 全部失败时返回主 provider 的原始错误 | 同上 |

### A.2 当时的唯一缺口：逐块延迟

现成网关均不提供「中途给流加延迟」。LiteLLM 只有 `LITELLM_MAX_STREAMING_DURATION_SECONDS`
（限制流总时长、超时终止），是掐断而非节流。当时的补法是 Bifrost 插件层的
`HTTPTransportPreHook` / `HTTPTransportPostHook`，用 Go 编译成 `.so` 加载，代价是必须
使用动态构建版 Bifrost。该功能已于 §1.7 砍掉。

另注（仍然成立）：Bifrost 限流按「时间窗内 N 个请求」计算，不是严格最小间隔，
毫秒级最小间隔仍需自研。

### A.3 备选与风险

- LiteLLM 同样覆盖全部核心需求（`model_name` 同名分组、`order` 优先级层、`fallbacks`、
  按 429 与失败率触发的 `cooldown_time` 自动恢复、`rpm`、`tpm`、`latency-based-routing`），
  但 2026 年发布 12 个安全公告（3 个严重，含未授权 RCE 与预认证 SQLi），修复起点为
  ≥ 1.84.0，且管理面板不可暴露公网；另外没有内置插件层。参见
  [自托管网关对比](https://cuihuan.github.io/awesome-ai-gateway/compare/best-self-hosted-ai-gateway-2026.html)。
- Bifrost 独立实测额外开销 +0.62 ms/请求，为三家最低。
- Kong、Higress、Envoy AI Gateway 适合已跑 K8s 的场景，本机单机不必采用。
- TensorZero 仓库已于 2026-06 归档只读，无上游维护，不作为新项目默认。
- 已排除：new-api（价值在多用户 key 分发与计费面板，本场景不需要）、CrossLink（太新）、
  CLIProxyAPI 与 sub2api 与 OmniRoute 等（账号池，存在厂商 ToS 与封号风险）。
