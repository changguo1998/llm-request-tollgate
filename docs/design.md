# llm-request-tollgate — 顶层设计

> 状态：v1 已实现, v2 调度模型 (§5.5) 也已实现并替换掉 D3 / D10 / D11 / D13 / D16 与
> F3 / F4 / F11；代码是 main.go 单文件代理, 自测是 test/ 假上游 (17 组 131 项断言全绿),
> 另有 go test 的调度与端到端用例 (2026-10-13)。实现形态是自研单文件代理, 不加插件,
> 不引入现成网关。
> 文末附录保留已否决路径的调研结论。

## 1. 需求

### 1.1 模型路由

- 一个对外模型名绑定一组后端候选：`逻辑名 → [(上游, 该上游的真实模型 id), ...]`,
  顺序即优先级。必须逐上游写真实 id —— 同一个名字在不同上游可能指向不同版本。
- 别名表即白名单：未命中的模型名直接返 404 (OpenAI 兼容 error 体), 不猜上游；对外
  `GET /v1/models` 只返回逻辑名清单。
- 响应体与流 chunk 里回显的 `model` 改回逻辑名, 对外隐藏 provider。

### 1.2 失败切换

- provider 报错时代理就地换后端重发, 对 agent 透明 —— agent 只看到等待变长。
- agent 侧不改：不调整各 agent 自己的重试策略与配置。
- 代理不再重试时, 把真实错误原样交给 agent, 保留原始状态码与关键响应头。
- 切换只能发生在首字节之前 (§2 第 1 条)。

### 1.3 请求侧限速

- 三类特殊限制分别处理, 其余错误走通用兜底 (v2, §5.5.2)：
  **并发限制** (信号量, 上限自适应, 起点 1)；
  **流量限制** (每上游一条队列, 出队节拍至少 500ms)；
  **额度限制** (供应商侧硬限制, 按上游返回的错误识别, 命中即锁该供应商; 额度是 key 级
  共享的事实, 所以锁整家)。
- 按「上游 + 凭据」分组, 跨 agent 共享同一份计数；各上游互不拖累。
- 覆盖机器上所有 agent：本机所有会发模型请求的进程都必须走代理 (§2 第 5 条)。
- 目的是防止频繁访问上游, 不是节省 token 花费。

### 1.4 金额预算控制

- 超限最终由上游硬限额执行；**代理不自己拦请求**, 只按上游返回的错误反应 (锁该供应商、
  切下一个候选)。那家的 key 自带 3h/12h/24h 三层预算, 平台侧硬拒, 是最硬的一层。
- **预算不进服务程序**：服务只写日志, 不重建窗口累计、不标定折算系数、不落盘预算状态。
  额度分析交给一个**独立的分析程序** (计划中, 见 O10), 既不随服务启动, 也不做成代理的子命令。
  例外是只读观测面 (D21): 它只回答「此刻什么在进行、卡在哪一步」, 不做任何累计与折算, 也不落盘。
- 实测 (2026-10-13)：USTC 的余额接口只认 cookie 会话, 不接受 `sk-` key (401), 代理调不到,
  该路线已放弃 (O7)。
- 花费不在代理内估算 (不建 token 单价表)。

### 1.5 可观测

- 看得到实际用了哪个后端、用了多少量 (token 口径：`prompt` / `cached` / `completion` / `total`)。
- 每次请求记：逻辑名、上游、真实模型 id、用量、是否缺 usage、等待环节与时长、被挡下的原因。
- 本地查询面：JSONL 日志 + `-summary` / `-usage` 汇总命令；日志按本地日历天轮转 (§4.4)。

### 1.6 形态

- 独立代理程序 (进程外), 不做 agent 内插件 (理由见 §3)。

### 1.7 已砍掉

- **响应侧逐块 TPS 节流** (拖慢上游吐字) 与实时 TPS 展示。它是唯一必须在「写给客户端之前」
  干预的功能；砍掉后不再需要插件层, 也就没有动态链接构建与依赖版本对齐的负担。

## 2. 已探明的硬约束

1. 透明重试只在「给下游写出第一个字节之前」成立。开始写之后只能把错误原样传下去 ——
   重发会让下游收到两段拼接的输出, 比报错更糟。
2. 错误原样透传分两种位置：
   - 首字节之前：原封不动的 HTTP 错误响应 (状态码 + 响应头 + 响应体)。
   - 流开始之后：响应头已发出、不可更改, 只能用流内约定的报错形态表达 (本设计取 SSE error
     事件后关流, F6), 不能塞 JSON 错误体, 否则下游可能把半截流当正常结束。
3. 客户端对「两块之间的间隔」有 5 分钟静默线 (宿主 `streamIdleTimeoutMs`, 默认 300000,
   可配)。代理的出流节奏与任何等待都必须留在此线以内。
4. 代理成为本机唯一模型出口, 因而是单点故障；密钥也集中到代理一处。
5. 所有流量必须真的走代理：只要有一个 agent 直连上游, 限速总闸即失效。
6. 限速必须按「上游 + 凭据」分组, 不能做成单一全局总闸, 否则不相关的上游互相拖慢；
   同一上游同一凭据的计数需要跨 agent 共享。
7. 代理只监听本机、走 HTTP 即可, 不需要自建 CA 或签发证书 —— 各 agent 的 base URL 直接
   指向 `http://127.0.0.1:8787/v1` (端口可配, F8)。

## 3. 为什么不用插件

**决定性原因：限速要覆盖同一台机器上的所有 agent。** 进程内插件只能限住它所属的那条链,
管不到同机其他 agent；而限速一旦漏掉任何一个直连上游的进程, 总闸即失效。同机的多个 agent
当前就配置了指向同一批上游的 base URL, 也就是说它们已经在同一份配额池里互相挤。只有把
出口收到代理这一层才能统一覆盖 (各 agent 的 base URL 都可以改)。

宿主确实在请求错误处暴露了 waterfall 钩子, 注册监听器即可否决内建重试并改判, 能在单侧实现
自动切上游, 不碰上游也不需要代理。但它覆盖不到其他 agent, 且与代理机制重叠, 故不用。

## 4. 已定案的实现（自研单文件代理）

### 4.1 形态

单进程, 四件事：别名表、按「上游 + 凭据」分组的并发计数与出队队列、自建转发循环
(`Transport.RoundTrip` + 手工头透传；没用 `httputil.ReverseProxy`, 因为集中 fallback 要在
给下游写第一个字节之前读上游状态码并可能重发请求体)、响应 usage 提取与逐笔记账。

- 所有 agent 打同一个进程, 计数天然跨 agent 共享, 无需 Redis 或数据库。
- 分组键是「上游 + 凭据」, 即一个 base URL 加一把 key 一份计数。一个上游只配一把 key,
  没有轮换 (O6)。
- 并发计数、队列与错误计数都在进程内, 重启清零。落盘的只有定时锁的到期时刻 (D20) 与
  探测统计 (`var/probe.json`)；预算与用量相关的状态一律不落盘, 日志就是全部记录 (D12)。

### 4.2 别名表

- 结构：`逻辑名 → [(上游, 真实模型 id), ...]`, 顺序即优先级, 兼作路由表。
- 别名表即白名单：未命中的模型名直接返 404, 不猜上游。
- **最容易踩的坑**：真实模型 id 与逻辑名不是一一对应。`deepseek-v4-flash` 在 ustc / group
  与 arkcp 下不是同一个版本, 因此必须逐上游写各自的真实 id, 不能按名字在候选间平移。

### 4.3 限速与用量

- 限速三件事 (v2, §5.5)：并发靠信号量 (上限自适应, 起点 1)；流量靠每上游一条队列, 出队
  节拍至少 500ms；额度不自己记账, 只认上游返回的额度类错误。
- 等待上限：等信号量 5 秒、排队 10 秒 (不再是 60 秒), 超过返 429 带 `Retry-After`, 交给
  agent 自身的重试。等待与上游首字节之和仍远小于客户端 5 分钟静默线 (§2 第 3 条)。
- 用量获取：转发时把请求体的 `stream_options.include_usage` 强写为 true, 从流末 usage
  chunk 取用量；非流式直接读响应体。`/responses` 没有 `stream_options`, 不做注入, 用量按
  `input/output_tokens` 取并在记账时与 `prompt/completion_tokens` 归一, 流以
  `response.completed` 判正常收尾 (该 API 不保证 `[DONE]`)。
- 缺 usage 时按字符数估 (口径见 F7), 并把「没拿到 usage 的请求数」记入日志, 不能静默。
- 只记 token 用量, 不建单价表、不估算花费 (§1.4)。

### 4.4 可观测

- 每次请求记：逻辑名、命中上游、真实模型 id、token 用量、是否缺 usage、等待环节与等待时长。
- 被挡下而没发出去 (429) 时额外记原因：没抢到信号量 / 排队超时 / 供应商处于锁中或退避中。
- 规则表没覆盖到的上游报错, 把上游 id + 状态码 + body 前 200 字写进服务日志 (journal),
  用来按真实文案补规则 (providers-api.md §1.2、§3.2)。
- 查询面**计划**搬到一个独立的分析程序 (O10, 语言不限, 不必是 Go), 只读日志、不随服务启动。
  现在的三个形态都还是代理二进制上的模式：`-summary <log|dir>` 按 逻辑名 + 来源 聚合
  请求数 / 429 / 等待 / 缺 usage / token 用量 (传目录跨归档读)；`-usage <log|dir>` 按
  上游 + 真实模型 × 窗口 (`-windows`, 缺省 3h/12h/24h) 列出用量；`-tui` 是实时那一版 (见下)。
- 用量记四种口径：`prompt` / `cached` / `completion` / `total`。上游的四种缓存字段名
  (`prompt_tokens_details.cached_tokens`、`input_tokens_details.cached_tokens`、
  `prompt_cache_hit_tokens`、`cache_read_input_tokens`) 都解析进来。
- 日志按本地日历天轮转：跨天 (或隔天启动) 时把上一段日志归档为 `<base>-YYYY-MM-DD.jsonl`,
  同名不覆盖 (依次 `-1` / `-2`)；不自动删除或压缩, 留存交给外部。汇总跨归档读。
- **正在发生什么**是日志答不了的那一半 (日志只有结局), 所以服务另开一个只读观测面
  (D21): 进行中的请求 (逻辑名 / 当前候选上游 / 真实模型 / 卡在哪一步) 与每个候选的队列、
  自适应并发上限、锁与退避。它纯内存、不落盘、不参与记账与调度判断, 重启即清空 —— D12 的
  「日志是唯一事实来源」不受影响, 观测面只补「这一秒」。
- `-tui` 是这套观测面的消费者, 也是 O10 期望的那个独立分析程序的第一版 (仍是同一个
  二进制; 前三个页只读日志与观测面, 不改转发路径): `active` 页把进行中的请求按调度流程
  分块 (获取信号量 / 排队 / 等模型窗口 / 等首字节 / 接收中 / 已失败); `models` 页先列每个
  上游的并发 / 额度锁与出队节拍, 再把真正进过队列的 `上游/真实模型` 的队列、退避、熔断锁与
  按模型求和的路由聚合 (窗口 6h, 跨归档读) 合成一张表, 不出现逻辑名;
  `events` 页看加锁 / 熔断 /
  退避 / 解锁 / 换候选 / 错误 / 慢请求。另一个进程里跑时用 `-tui-state <base>` 走
  `GET /v1/state`。
- `settings` 页 (D22) 是唯一可写的一页: 上半改配置里的 `gate` 调度参数 (写回
  `config.local.json`, 只动 `gate` 段), 下半调 store 里的 `tollgate_priority`, 右栏实时
  预览候选顺序 (`m` / `p` / `g` 切模型 / provider / 调度参数), `s` 保存并热加载 /
  `r` 重生成配置 / `h` 热加载。它不碰转发路径, 改的是配置源头。

### 4.5 实测依据（直连探测）

- 四个上游的 `/chat/completions` 与 `/responses` 均可直连成功；其中一家首字节约 19 到 25 秒,
  属常态, 须放大超时而不是当作故障。
- 有一个上游连 `/models` 都不提供, 其路径形态须手工确认后再接入。
- 各家都在模型名不存在时先报错 (403 / 400 / 404), 所以「模型名写错」表现为 4xx 而不是 5xx,
  重试判定要据此区分。
- 真实模型 id 清单须以各上游 `/models` 为准；不同上游的清单规模差异很大。
- ustc 与火山 ARK 都要求认证头带 `Bearer ` 前缀, 裸 key 会被判 "Malformed API Key"。

### 4.6 已知缺口与风险

1. 首字节之后不能切后端的物理约束仍在：集中 fallback 只覆盖首字节之前的失败 (传输错误 /
   429 / 5xx), 流开始后的失败按 F6 走 SSE error 事件。
2. 代理内看不到花费, 只有 token 用量；缺 usage 的上游会让用量偏低, 兜底估算与计数必须做。
3. 代理成为唯一出口即单点故障, 密钥集中于此；常驻与自检已具备 (O1), 单点本身消不掉,
   只能靠自动拉起缓解。
4. 一个上游只配一把 key, 那把 key 失效时该上游整体不可用 (O6)。
5. 超限的表现是「等待变长 + 换模型」, 不是被代理拒绝；平台侧硬限额仍是最后一道 (D13)。
6. 被锁或被队列挡下时**不溢出**到其它空闲候选 (D15 有意为之), 因此要把整条候选链试完才报错。

### 4.7 验证顺序

1. 起最小代理 (只做别名与转发), 把一个真实 agent 指过来跑一轮带工具调用、思考块与长流的
   会话, 确认流式逐块透传、没有被缓冲或改写。(已完成)
2. 加 `stream_options.include_usage` 注入, 核对客户端收到的 usage 与上游一致。
3. 加信号量与队列 (v2, 已完成)：出队节拍设一个明显的值, 验证两次请求的实际间隔；并发
   上限从 1 起步, 两个 agent 同时发, 验证「并发满 → 试探 → 上限 +1」与拿不到槽位时的 429
   行为 (自测的 ratelimit / fallback-gate 两案)。
4. 核对用量：日志里每笔的 token 与上游一致, 且「缺 usage」有计数；再量一次代理自身开销。

**起步方式**：第 1 至 4 步先用本地假上游自测 —— 假上游按脚本回放含工具调用、思考块与长流的
SSE, 真 agent 指向代理；接上真上游后重跑同一套 (D9)。

### 4.8 配置形状（JSON）

门控参数 (v2) 收进一个所有上游共用的 `gate` 块, 不再挂在每条上游记录上。

```json
{
  "listen": "127.0.0.1:8787",
  "log_path": "var/requests.jsonl",
  "timeouts": { "connect_ms": 10000, "response_header_ms": 120000, "stream_idle_ms": 240000 },
  "gate": {
    "interval_ms": 500,
    "sem_wait_ms": 5000,
    "queue_wait_ms": 10000,
    "concurrency_lock_ms": 3600000,
    "quota_lock_ms": 600000,
    "breaker_lock_ms": 300000,
    "retry_backoff_ms": [10000, 20000, 30000]
  },
  "upstreams": [
    {
      "id": "ustc",
      "base_url": "https://example.invalid/v1",
      "auth_header": "Authorization",
      "key_env": "USTC_API_KEY",
      "headers": {},
      "include_usage": true
    }
  ],
  "aliases": {
    "deepseek-v4.1-flash": [["ustc", "deepseek-v4.1-flash"], ["group", "deepseek-v4.1-flash"]]
  }
}
```

- `base_url` 自带路径前缀 (含 `/v1`), 以 §4.5 的实测形态为准。`auth_header` 与 `headers`：
  有的中转不用 `Authorization` (例如 `api-key`), 有的要额外头。`key_prefix` 是认证头里的
  scheme, 缺省对 `Authorization` 用 `"Bearer "`, 其余头直接放裸 key。
- `key_env`：配置只存环境变量名, 真 key 启动 / 热加载时从环境取, 不落盘；缺省回落 `key`。
- `gate`：v2 全局块, 所有上游共用；字段含义见 §5.5.4。并发上限不在配置里 (起点固定 1),
  出队节拍由 `interval_ms` 给 (缺省 500ms)。
- `errors`：每个上游一份错误分类规则, 每类是一个规则数组, 单条规则是
  `{ "status": [400, 422, 429], "contains": ["budget_exceeded", "Budget has been exceeded!"] }`
  —— `status` 在列表内 (缺省 = 任意状态码) **且** 匹配文本里出现 `contains` 任一子串才算命中；
  匹配文本取 `error.type + error.code + error.message` (小写), body 不是 JSON 时退回整段 body。
  判定顺序固定 `quota → concurrency → 其他` (额度不可重试, 必须先判)。逐家规则与判定流水线见
  [providers-api.md](providers-api.md) —— 那份文档里的可选 `rate` 档动作与通用兜底一致,
  本实现不单独建类。缺省空表 = 全部走通用兜底 (不会触发任何锁)。
- `include_usage`：per-upstream 开关, 用来承接 O8 的探测结果。
- `aliases` 的值是 `[[上游 id, 真实模型 id], ...]`, 顺序即优先级。

### 4.9 实现陷阱

1. gzip：非流式要读 usage 就得能解压, 出站要删掉下游传来的 `Accept-Encoding`, 让 Transport
   自己协商并透明解压。
2. SSE 按行解析而不是按 chunk 切：`data:` 可能多行。
3. 客户端断开：还没出队的话先丢掉队列里那一项、释放并发信号量, 且不重复记账。
4. 请求体需整体缓冲才能改写 `model` 与 `stream_options` (带 base64 图片时可能几十 MB)；
   非流式响应也要缓冲才能读 usage。
5. 头部：除认证头 (按上游替换)、hop-by-hop 头与 `Accept-Encoding` 外原样透传, 不新增头部
   (不经 `ReverseProxy`, 故无 `X-Forwarded-For`)；代理自产的 4xx 用 OpenAI 兼容 error JSON
   体, 429 另带 `Retry-After`。

### 5.5 v2 调度模型（已实现）

把「限速闸」由「令牌桶 + 信号量 + 整请求共用排队预算」换成**每上游一条队列 + 自适应并发
上限**, 并把报错分成三类特殊限制加一类通用兜底。额度不再由代理记账拦截, 只按上游返回的
错误反应。D3 / D10 / D11 / D13 / D16 与 F3 / F4 / F11 均由本节取代。

#### 5.5.1 主流程

```
请求
→ 选候选（别名候选顺序 = 优先级，跳过该模型处于锁内或正在退避的候选）
→ 取信号量
   a. 5s 拿不到 → 下一个候选
   b. 拿到 → 进该上游的流量队列（只管 500ms 出队节拍）
      b1. 排队 10s 没轮到 → 下一个候选
      b2. 出队 → 进该模型的队列（不等节拍；只在熔断锁 / 退避时才等，上界同为 10s）
      b3. 模型队列放行 → 发送
          - 正常结束
          - e1. 额度限制 → 整家锁 10min + 整队迁移 → 下一个候选
          - e2. 其他报错 → 该模型连续错误计数 +1 → 该模型退避 → 回到候选选择
                n=1 等 10s, n=2 等 20s, n=3 等 30s（下一轮选候选时直接跳过它）
                c. n=4 → 熔断：只锁该模型 5min + 整队迁移 → 下一个候选
→ 候选链试完仍不行 → 报错
   被锁 / 退避 / 排队挡下而没发出去的：合成错误说明原因
   真发出去失败的：透传最后一个候选的状态码与 body
```

- 没有整请求总时间预算：每换一个候选重新给 5s + 10s（两段队列共用后一个预算）。
- 并发满时, 若允许试探 (未锁且没有别的试探在进行) 就先试探, 不允许试探才走 a 的 5s 等待。
- 候选顺序永远是别名表里的顺序, 不做负载均衡 (D15 不变)。

#### 5.5.2 三类特殊限制与通用兜底

**并发限制**（核心是信号量）

- 上限自适应：起点 1, 不设天花板, 不落盘 (每次重启从 1 重新爬)。
- 并发满且并发锁未生效 → 挑一笔做试探, 同一时刻只允许一笔试探在进行。
- 试探不占用信号量 (纯超发), 失败无需释放。
- 试探成功 → 上限 +1, 这一笔继续正常流程 (仍走队列节拍)。
- 试探失败且错误明确是「并发上限」→ 锁并发上限 1h, 不等那 5s, 直接下一个候选。
- 试探失败是别的错 → 不锁并发, 按 e1 / e2 分流。

**流量限制**（两层队列）

- 上游一层**流量队列**（FIFO, 只保证出队节拍）：发送间隔至少 500ms, 上一次发送满 500ms 才能
  发下一笔；队列空一阵后来请求可以立刻发。别家模型的退避不会堵在这里。
- 模型一层**模型队列**：出队即发, **不等节拍**；只有该模型被熔断锁住、或正在退避时才等,
  等到解锁 / 退避结束或 10s 上界（超时换候选）。
- 只有拿到信号量的请求才进队列；队列长度天然被并发上限卡住, 不单独配长度, 也没有「队列满」
  判定 —— 拿不到信号量那一步 (a) 就是「去排下一个候选」。
- 请求选到正在退避的模型时**直接跳过**（与熔断锁同等对待）, 不进它的模型队列白等：
  退避 10/20/30s 比排队预算长, 等也等不到。

**额度限制**

- 供应商侧硬限制, 请求侧不记账 (token 数只写进日志, 分析在服务之外)。
- 判定：每个 provider 各配一份「状态码 + body 关键词」规则, 状态码在列表内且关键词命中才算；
  顺序固定 `quota → concurrency → 其他`。逐家规则与判定流水线见 providers-api.md, 规则表
  缺省为空 (全部走通用兜底)。
- 命中 → 整家锁 10min + 整队迁移。

**通用兜底**（前三类以外）

- 退避是**模型级**的（`上游/模型`）, 不是每笔请求各自的：该模型维护连续错误计数 n, 成功清零。
  同家别的模型的成功不清它的计数, 它的退避也不挡别的模型出队（两层队列: 退避只压模型队列）。
- n=1 暂停 10s, n=2 暂停 20s, n=3 暂停 30s, n=4 进熔断 (只锁该模型 5min)。
- 退避期间新请求照常进该上游的流量队列；选候选时看到该模型还在退避就直接换下一个候选,
  不会为它多等（排队预算 10s 也等不到 10/20/30s 的退避）。

#### 5.5.3 两把锁

1. **并发上限锁** (1h)：只锁「超发试探」这一件事, 候选本身照常用。
2. **定时锁**：一个到期时间戳加一个原因标记, 同一机制两种作用域 —— **整家锁**（额度 10min,
   额度是 key 级共享的事实）与**模型锁**（熔断 5min, 只锁出错的 `上游/模型`）。模型锁更具体,
   两把同时在时以它为准; 同一作用域内先后触发取更晚的到期时间。两种都落盘, 重启仍生效。
   加锁动作里含一步：把该候选队列里排队的请求**整队迁移**到下一个候选重新排队。

#### 5.5.4 配置

新增一个全局 `gate` 块 (完整样例见 §4.8), 所有候选共用, 不按候选配：

- `interval_ms` 500：出队节拍下限。
- `sem_wait_ms` 5000 / `queue_wait_ms` 10000：等信号量与排队的上限。
- `concurrency_lock_ms` 3600000 / `quota_lock_ms` 600000 / `breaker_lock_ms` 300000：两把锁的时长。
- `retry_backoff_ms` [10000, 20000, 30000]：通用兜底的退避序列。

同时删掉：

- 每条上游的 `limits.rate_per_sec` / `burst` / `concurrency`, 以及 `breaker_fail` /
  `breaker_cooldown_ms` / `budget.cooldown_ms`。
- 全局的 `quotaHints` / `rateHints` 关键字表, 改成每个 provider 一份错误分类规则 (`errors`,
  形状见 §4.8)。
- 并发上限不进配置 (起点固定 1), 出队节拍也固定 500ms。

整个 `budget` 子系统 (窗口累计、折算系数、`refresh_sec`、状态文件) 从服务里删掉, 服务只写
日志；分析交给独立程序 (计划中, O10)。

#### 5.5.5 其他约定

- 客户端断开或取消 → 已入队的项丢弃并释放信号量。
- 试探那一笔不占信号量, 失败无需释放；同一时刻只允许一笔试探在进行。
- 错误分类规则落地前, 规则表默认空 = 全部走通用兜底, 暂时不会触发并发锁。
- 自测已按 v2 重写 (17 组 131 项断言), 另有 `go test` 的调度核心与端到端用例
  (`gate_test.go` / `proxy_test.go`): 出队节拍、超发试探放宽上限、两把锁、错误归类、
  退避与熔断、锁状态落盘、以及经代理转发的完整链路。

## 6. 宿主侧背景（引用本机时需重核）

- 宿主有唯一一处决定用哪个 provider 的内部接口, 每次尝试前都会跑一次, 重试也会重跑它。
- 另有决定「要不要再来一次」的内部接口, 宿主的重试插件挂在那里。
- 传输层改写 provider 对主链路无效, 因为上游此时已解析成具体适配器。
- 宿主插件链是 waterfall 语义：监听器最外层先跑, 不调 `next()` 即否决整条链。
- 宿主的重试插件只决定「重试同一步骤」, 本身不切换上游；策略按 provider 配置, 退避带抖动,
  并支持上游的 `Retry-After`。
- 默认可重试错误码只有 `EMPTY_RESPONSE`、`RATE_LIMIT`、`SERVER`、`TIMEOUT`、`TRANSPORT`；
  `QUOTA` 与 `AUTH` 不在其中, 宿主侧不会重试。
- 上游 usage 在流末 chunk 中给出, 宿主据此记账 —— 这一点对代理的用量提取有利。

## 附录 A. 已否决路径：现成网关调研（保留备查）

> 2026-10-12 的结论是「不自研, 采用现成开源网关」, 主选 Bifrost (Go)、备选 LiteLLM (Python)；
> 该结论随后由 §4 推翻。当时的判断依据仍然有效：网关最常见的故障不是路由, 而是工具调用 /
> 思考块 / 流式翻译被破坏, 所以实测不能只发 hello world, 要把真实会话过一遍。以下是备查事实。

- **Bifrost** 覆盖原需求的大部分：model aliasing、按序 fallback、provider 级 rate limit 与
  budget、virtual key 承载跨 agent 共享计数、请求日志与 Prometheus 指标、自定义 provider。
  独立实测额外开销 +0.62 ms/请求, 为三家最低。缺口是「中途给流加延迟」(即已砍掉的逐块 TPS
  节流), 只能靠插件层的 `HTTPTransportPreHook` / `HTTPTransportPostHook` 补, 代价是必须用
  动态构建版。另注：它的限流按「时间窗内 N 个请求」算, 不是严格最小间隔。
- **LiteLLM** 同样覆盖核心需求 (`model_name` 分组、`order` 优先级层、`fallbacks`、按 429 与
  失败率触发的 `cooldown_time`、`rpm` / `tpm`、latency-based routing), 但 2026 年发布 12 个
  安全公告 (3 个严重, 含未授权 RCE 与预认证 SQLi), 修复起点 ≥ 1.84.0, 且管理面板不可暴露
  公网；另外没有内置插件层。
- **其他**：Kong / Higress / Envoy AI Gateway 适合已跑 K8s 的场景, 本机单机不必采用；
  TensorZero 仓库已于 2026-06 归档只读；new-api (多用户 key 分发与计费面板, 本场景不需要)、
  CrossLink (太新)、CLIProxyAPI / sub2api / OmniRoute (账号池, 有 ToS 与封号风险) 均已排除。
